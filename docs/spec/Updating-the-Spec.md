# Updating the Spec

This document is generated. `docs/spec/*.md` on `main` is the source of truth; the GitHub wiki is a
mirror of it, published by a job that deletes any wiki page not present in `docs/spec`. **Never edit
a wiki page directly** — a scheduled run will silently discard the edit the next time it mirrors, and
in the meantime the wiki and `docs/spec` disagree with no warning to anyone. All durable changes go
into `docs/spec` on `main` (via a normal pull request) or are generated by the pipeline below.

## The page set is this table, not `Home.md`

`Home.md` is itself regenerated on every run, including its page index. **Adding a page to the spec
means adding a row to the page-set table carried in `scripts/spec/prompt.md`** (the prompt handed to
the model) — a link placed only in `Home.md` is overwritten and lost on the next regeneration, and a
page that exists in `docs/spec` but is missing from that table is never linked from anywhere,
because nothing regenerates `Home.md`'s index from the table except the same run that would also
overwrite a hand-added link. In practice: to add a page, edit the table in `scripts/spec/prompt.md`
first, then let the next run (or a manual one) create the page and re-index `Home.md`.

## The pipeline: collect → generate → verify → publish

Defined in `.github/workflows/spec-wiki.yml`, on a `schedule: cron '0 */6 * * *'` trigger (every 6
hours) or `workflow_dispatch`:

```
scripts/spec/collect.mjs   (no model)  -> spec-facts.json: module graph, exports, tests,
                                          workflows, open issues -- ground truth
copilot (model)                        -> docs/spec/*.md, one page at a time from
                                          scripts/spec/prompt.md, using spec-facts.json
scripts/spec/readability.mjs (no model) -> wraps exposed examples in collapsible,
                                          coloured technical-detail callouts
scripts/spec/verify.mjs    (no model)  -> fails the build if the prose references
                                          anything that does not exist, or omits a domain
scripts/spec/conflicts.mjs (no model)  -> reports open issues that demand opposite things
                                          (spec-decisions.md), which verify.mjs cannot catch
```


</details>
The split exists because handing a model the repo and asking for a spec produces prose that drifts
from the code immediately and is uncheckable by reading it — the failure mode is the prose's
*relationship* to the code, which a reader never has in front of them. `collect.mjs` and `verify.mjs`
are the two halves with no model in the loop, and they are what make the artifact trustworthy rather
than merely plausible.

### Running the mechanical halves locally

```
node scripts/spec/verify.mjs --facts spec-facts.json --dir docs/spec

```

`scripts/spec/verifyParity.mjs` is a unit test (run by `npm test`) that holds the workflow's
CI-verification job to the same command set CI itself runs, so the two cannot silently diverge.

## Every finding `verify.mjs` can emit

| Finding | Meaning |
| --- | --- |
| `invented-path` | The page names a `src/`, `scripts/`, `packages/`, or `plugins/` file (with a `.js`/`.jsx`/`.mjs`/`.ts`/`.tsx` extension) that is not in `spec-facts.json`'s `modules[]`. Fix by correcting the path or removing the claim. |
| `unknown-issue` | A `#123`-style reference does not resolve to any issue or PR number the collector found. Fix by correcting the number or removing the reference. |
| `uncovered-domain` | One of `spec-facts.json`'s `domains[]` is not mentioned by name anywhere in the page set. Fix by adding a page or a section that names it. |
| `uncovered-key-module` | The single largest module in some domain is never named anywhere. A domain can pass the coverage check above by a passing mention while its substance is absent, so this is a second, stricter check pinned to a real file. |
| `thin-page` | A page is under 250 words — the floor below which it cannot carry an architecture, a data format, and its rationale. |
| `no-examples` (page `(all)`) | No fenced code block appears anywhere in the page set. A spec that never shows a concrete artifact cannot be rebuilt from — prose cannot substitute for a real signature or file format. |
| `exposed-technical-detail` | A fenced example appears in the main reading flow instead of a collapsible `<details>` block. |
| `unlabelled-technical-detail` | A collapsible technical block has no `<summary>` describing what it contains. |
| `uncoloured-technical-detail` | A collapsible technical block lacks a GitHub alert immediately before it, so optional depth is not visually distinct. Alerts cannot be nested inside `<details>` because GitHub renders nested alert markers as literal text. |
| `technical-doc-code` | `Technical-Architecture.md` contains a fenced block other than a Mermaid diagram. The deep-dive may contain architecture and principles, never implementation code. |
| `missing-technical-doc` / `unlinked-technical-doc` | The architecture deep-dive is absent or cannot be reached from `Home.md`. |

`invented-path` and `unknown-issue` findings are fatal (nonzero exit); `uncovered-domain` and
`uncovered-key-module` are fatal too — all are reported together, grouped by kind, with the first 25
instances of each kind and a count of the rest.

## Issue references: open issues only, by design — with two exceptions to word around

The path/issue check validates most issue references against `spec-facts.json`'s `validRefNumbers`,
a broad set covering **open issues, closed issues, and pull requests** (PRs share the issue-number
namespace, and `gh issue list` excludes them, so `collect.mjs` unions `gh issue list --state all` and
`gh pr list --state all`). But **`Roadmap.md` is checked against `openIssues` only** — the narrower
set — because Roadmap is a *gaps* page: it presents open issues as the system's current, live state,
so a closed issue cited there as a still-open gap is stale and wrong, and the narrower check is what
catches that. Every other page is rationale/history, where citing a closed issue or a PR as evidence
for a past design decision is legitimate, so it is checked against the broad set instead.

The practical consequence for whoever edits a page: **on `Roadmap.md`, cite only currently-open issue
numbers.** On any other page, if you want to cite something that has since been closed, or a pull
request, write it in prose (`PR #123`, `issue #123 (since closed)`) rather than relying on the bare
`#123` pattern to be silently accepted — it will resolve under the broad set, but the reviewer should
be able to tell from the words around it that it's historical, not a live claim.

`verify.mjs` also runs a separate, **non-fatal** informational pass on every page (not just
Roadmap): any `#123` reference that resolves but to a closed issue or a PR is printed to stdout as
`closed refs (informational)` so a human reviewer can check the framing — this never fails the
build and is not gated behind a flag, because an opt-in drift check nobody has to turn on has the
same failure mode as no check at all.

## Publishing

Two independent paths write the wiki, and `GITHUB_TOKEN` cannot use either directly — a repo's
default Actions token cannot push to `<owner>/<repo>.wiki.git`, which is a separate git repository
outside its scope.

1. **The scheduled `publish-wiki` job** in `spec-wiki.yml`, gated on `secrets.WIKI_TOKEN` — a
   personal access token with `repo` scope, added once as a repository secret. If the secret is
   absent, the job logs a notice and exits 0 (skipped, not failed), so the generate-and-verify loop
   works with zero setup and publishing is opt-in.
2. **`scripts/spec/publish-wiki.ps1`**, run locally with a `gh`-configured token that carries `repo`
   scope. This is the ad-hoc path: no pull request, no review gate, immediate. Anything published
   this way that is not also landed in `docs/spec` on `main` is reverted by the next scheduled mirror
   run, so treat it as ephemeral unless the same change is also committed.

Both paths mirror by deleting every `*.md` in the wiki checkout and copying `docs/spec/*.md` back in,
so a page removed from `docs/spec` disappears from the wiki rather than lingering as untraceable.

## Traps

- **`README.md` is not a page.** It exists in `docs/spec/` as provenance for a human browsing the
  folder on GitHub, not as spec content — `verify.mjs` explicitly excludes it (case-insensitively)
  from the page set it checks, and both publish paths delete it before copying, so it must never
  appear in the wiki. Do not add it to the page-set table.
- **A GitHub wiki link to a page that doesn't exist yet fails silently** as "create this page" rather
  than erroring — a typo'd `[Some-Page](Some-Page)` link looks fine in review and only reveals itself
  when a reader clicks it.
- **A brand-new wiki repository must be initialised once, by hand, in the GitHub web UI** (Wiki tab →
  "Create the first page" → Save) before either publish path can push to it — GitHub does not
  provision `<owner>/<repo>.wiki.git` on first push the way some other hosts do, and both `ls-remote`
  and `push` return an identical `Repository not found` before that first page exists, whether the
  cause is truly "uninitialised" or an unscoped token.
- **Do not restate the spec's own completeness bar inside a page.** Sentences like "a rebuilder can
  reconstruct this system from this page alone" are instructions to whoever writes the page, not
  content for whoever reads it — a page demonstrates completeness by being complete, not by claiming
  it.
- **Do not specify legacy/back-compat code paths as though they were the required forward design.**
  Where the code still carries a deprecated alias or a migration fallback, name it once as an aside
  scheduled for removal rather than folding it into the contract a rebuilder is meant to implement.
