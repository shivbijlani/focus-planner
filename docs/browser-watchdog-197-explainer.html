Why the browser watchdog kept reporting "all good" over three dead browsers

Issue #197 · Pull request #380 · written 1 September 2026

In one sentence: an automated job checked every hour whether three automation browsers were alive by asking "does the network port answer?" — but a browser can answer its port perfectly while being completely unable to do any work, and that is exactly the state all three were sitting in.

1. What these browsers are for

Some of Shiv's automation needs a real web browser: log into a site, read a page, fill a form. So three Microsoft Edge windows stay open permanently, each signed into a different account. They are called slots.

Each slot exposes a small local control channel on a numbered port (9225, 9228, 9229) so software can drive it. The automation does not launch a browser; it attaches to one of these already-open windows. If a slot is broken, anything needing a browser silently fails.

A scheduled job — the watchdog — runs every hour to make sure the three windows are healthy.

2. What actually breaks

When a browser window is hidden behind other windows for a while, Chrome and Edge deliberately freeze the page to save battery and CPU. This is a normal, intended feature.

A frozen page is a strange in-between state. It is not crashed. It is not closed. The browser is still running and still answers everything you ask about it. But the page's internal clock stops: anything that waits — even for a millisecond — waits forever.

Browser automation waits constantly ("wait until this button is ready", "wait for the page to settle"). So against a frozen page every operation hangs until it times out. The slot is unusable while looking perfectly fine.

The detail that makes it worse

The automation library inspects every open tab when it attaches. So one frozen tab is enough to make the entire slot unusable. Each of the three slots had exactly one tab, and it was frozen.

3. Why every health check said everything was fine

This is the heart of it. The watchdog's entire health test was this — open a network connection to the port, and if it succeeds, declare the slot healthy: 

$iar = $client.BeginConnect('127.0.0.1', $Port, $null, $null)
if ($iar.AsyncWaitHandle.WaitOne(1000)) { ... return $true }

if ($up) { Note "[slot ...] port ... already live - reusing." }

The catch: the part of the browser that answers the port is not the part that freezes. A browser is really two pieces — the browser process (windows, tabs, the control channel) and the renderer (the page itself). Freezing hits the renderer. The browser process keeps answering cheerfully.

So the watchdog was asking the one component that never breaks whether anything was broken.

What you can checkFrozen slot answers…Useful?
Does the port accept a connection?Yes ✅No
Does it report its version?Yes ✅No
Does it list its open tabs?Yes ✅No
Can the page run code that waits on a timer?No ❌Yes

Only the last question separates a working slot from a frozen one, because a frozen page's clock is precisely what has stopped.

The most frustrating part

The good test already existed and was already installed. It had been built earlier for this very issue. Nothing ever called it. Searching the watchdog for any mention of it returned zero results. The capability was finished, shipped — and wired to nothing.

5. What changed

The new watchdog does not invent a new opinion about browser health. It calls the two tools that already existed, in order:

StepWhat it does
1. AssessAsk each page to run code that waits on a timer. That is the question only a healthy slot can answer.
2. LaunchIf a slot is genuinely closed, start it — the one thing the old watchdog did do.
3. RepairIf a slot is frozen, thaw it in place. Nothing is closed, killed or restarted.
4. ConfirmAsk again. A slot is only called recovered because it now works, never because a repair was attempted.

It will never close one of your windows

These are real signed-in windows and may hold work in progress. Because of how Edge encrypts saved logins, a restart that goes wrong leaves that profile signed out, and only you can fix that. So the recovery stops at the one step that closes nothing. An automated test checks the code contains no way to kill a browser, so this cannot be lost by accident later.

And it now tells the truth when it fails

If a slot is still unusable after the repair, the job now exits with a failure code instead of reporting success. That sounds small, but it is what lets anything downstream notice and escalate rather than quietly carry on.

6. What is not fixed, honestly

The thaw does not hold

Un-freezing a page works immediately, but the window is still hidden, so the browser re-freezes it — measured at about eight minutes. This was seen again tonight: slots thawed at 18:20 were frozen again by 18:32.

So this change makes the hourly job able to recover the slots, which it previously could not do at all. It does not stop them freezing.

The obvious durable fix is to launch the browsers with settings that disable the freezing behaviour entirely — reasonable here, because these windows exist only to be driven by automation while hidden. That was tested tonight with a controlled experiment: two throwaway browsers, one with the settings and one without, both hidden.

The experiment failed to reproduce the problem, so it proved nothing

The browser without the settings never froze either. With no failure to prevent, there is no evidence the settings help. They are therefore not included in this change. Claiming a fix on that basis would be a guess dressed up as a measurement.

7. How to undo it

Two independent pieces, each reversible on its own:

  • The code: revert pull request #380 on GitHub.
  • The hourly job: the original script was preserved untouched beside the new one. Restore it with:
    install-browser-watchdog-skill.ps1 -Revert

Neither step touches a browser, a profile or a saved login.

8. Two things found along the way

  • An existing automated test is unreliable. It claims to use a made-up configuration but actually contacts the three real browsers, so it passes or fails depending on whether they happen to be frozen. It fails on the main branch for this reason, unrelated to this change. Reported, not fixed — it belongs to a different piece of work.
  • A setup script would undo an earlier fix. A separate, rarely-run "provision" step still installs the browser connectors in a style that was deliberately removed. It is not part of the hourly job, so nothing is broken today, but running that step would reintroduce it. Reported.
Verification: 893 automated tests pass; linting clean; three related guard suites green (18/18, 11/11, 17/17); and the change was run end to end through the real hourly entry point, taking three stuck slots to three working ones.
