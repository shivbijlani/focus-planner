Why the overnight agent kept re-reading enormous files — and what changed

A plain-language walkthrough. No prior knowledge assumed.

In one paragraph. Every night an assistant works through your task list. Before it touches a task, it was told to read that task's whole notebook — the running diary of everything you and it have ever said about that task. Those notebooks only ever get longer. One of them had reached 272 KB, which costs roughly 70,000 tokens of the assistant's limited reading capacity just to open. It now reads a short, bounded briefing instead. The worst notebook went from 272 KB to 15.5 KB, and not one byte of any notebook was changed, moved, or deleted.

1. The setup, for someone who has never seen this

There is a personal planner. Each task in it has a journal — a plain text file that reads like a chat thread between you and the assistant. You write what you want. The assistant replies with what it did, what it plans to do next, and what it needs from you. Everything gets appended to the bottom. Nothing is ever removed.

That design is deliberate and good: the journal is the honest record. The project's own rulebook says that if the assistant's internal bookkeeping ever disagrees with what is written in the journal, the journal wins. It is the human source of truth.

The assistant runs on a language model, and a language model can only hold a limited amount of text in mind at once. Call it a reading budget. Everything it reads on a given run comes out of that one budget.

2. The problem

The assistant's instructions contained this line, about any task it was about to work on:

Read each linked task's real material — its journal — in full.

That was a sensible instruction when journals were short. But journals only grow. Here is what they actually looked like when measured on 1 September 2026:

A typical journal was harmless. The outliers were not. And because one task can be linked to two or three others, a single night's planning could have been asked to read several of these at once — spending most of the reading budget before doing any actual work.

3. Why this was urgent rather than theoretical

The exact same failure had already happened once, on a different file — the settings file. It also grew without limit, and it was also read in full at the start of every run. The end state was documented:

  • it reached about 97% of the reading budget on every single call;
  • one run made 49 round-trips, sat in a running state for about nine hours, and never finished;
  • because it never finished, it blocked the every-30-minutes schedule behind it.

Nothing prevented a journal from doing precisely that. The only reason it had not happened yet is luck: no single task had happened to link enough large journals in one night. And the safety net for this — an automatic “this run has taken too long, stop it” timeout — has not been built yet. So if it had happened, there would have been no automatic recovery.

4. The fix, and the option that was deliberately rejected

The obvious fix is the one used on the settings file: write a program that rewrites the file smaller.

That was rejected here, on purpose. A settings file is a settings file. A journal is your own words, and four separate pieces of machinery read a journal by looking at its exact bytes:

  • a fingerprint of the file decides “has the human replied since I last wrote?”;
  • the position of certain markers decides “did the human actually approve this?”;
  • the Telegram bridge finds messages by those same markers;
  • a sentinel line divides your space in the file from the assistant's.

A rewriter that shifted one byte across any of those boundaries would either make the assistant re-answer finished tasks forever, or — much worse — make it believe it had your approval when it did not.

So instead of making the file smaller, the assistant now reads less of it. A new command produces a short briefing:

SectionWhat it contains
Your framingWhat you wrote at the top of the journal: the brief, the constraints, the links.
Your messagesEvery message you wrote, newest first — because a later decision overrides an earlier one.
Open questionsAnything the assistant is currently waiting on you for.
Latest replyThe assistant's most recent turn only: current status, current plan, what it last did.
Unanswered replyAnything you wrote after its last turn that it has not responded to.
PointersLinked tasks, and any attached documents listed by name and size — named, not read.

What it leaves out is the middle: the blow-by-blow history of every previous night. That is the part that grows forever, and it is the part that is almost never needed to decide what to do next.

Said plainly: what is read now, and what is not

Still read, in full and word for word: everything you ever wrote in that journal — your brief at the top, and every subsequent message of yours, newest first. Plus the assistant's most recent turn, its open questions, and anything of yours it has not yet answered.

No longer read: the assistant's older turns — the previous nights' run logs. Not your words. Its own.

That split is the entire safety argument, so it is worth being blunt about the risk it is managing. The thing a person would rightly worry about is: could the assistant now silently miss a decision you made? Three things are done specifically to prevent that:

  • Your messages are prioritised over the assistant's. An earlier draft of this only kept “your notes at the top”, which is what the old instructions literally said. On a journal that has been running for weeks that is badly wrong — on the largest one, the top section ends on 30 July, and every decision made in the five weeks after that sits below it. So a dedicated section collects every message of yours from anywhere in the file, newest first, because a later decision overrides an earlier one. The automated test suite deliberately breaks this and confirms the break is caught.
  • Anything skipped is announced, with a number. The briefing ends by stating exactly how many bytes it did not show, and the assistant is instructed that if the briefing suggests something is missing, it should open the full file. The bounded read is the default, not a cage.
  • The conclusions the assistant draws are unchanged. The machinery that decides “is this task waiting on the human?” and “did the human approve this?” was re-run across all 239 real journals before and after. All 239 verdicts were identical — including the single task that carries a genuine recorded approval, which still reads as approved. (That detail matters: “all 239 say no” would be easy to match by accident. Preserving the one yes is the real test.)

The honest residual risk: if a decision of yours is buried in the middle of an enormous stretch of your own writing, its middle can be trimmed — and the briefing will say so, in bytes, at that exact spot. In practice your messages are short and the assistant's are long, which is why this trade works.

5. The two promises, and how they are proved rather than claimed

PROMISE 1  Word for word. Every line in the briefing is copied exactly out of the journal. Nothing is summarised, condensed, or reworded. An AI-written summary of your decisions would be a quiet way of losing them, which is the whole thing being avoided.

PROMISE 2  Bounded. The briefing has a hard size ceiling no matter how large the journal is. And when something is left out, it says so and prints exactly how many bytes were skipped, plus how to read the full file if you really need it. Nothing is trimmed silently.

Both are checked by the tool itself, on demand, against the real file — not asserted in a comment. It was then run against every one of the 239 real journals:

Nothing was touched

The strongest guarantee here is a structural one: the tool has no ability to write to a journal at all. It is a reader. There is no save path in it to get wrong.

That was confirmed rather than assumed. The command that fingerprints all 239 journals and decides which tasks count as “waiting on you” was run before and after those 239 reads, and produced a byte-for-byte identical result (same 182,361 bytes, same SHA-256 fingerprint). Separately, the approval check was run task-by-task against both the old and the new code across all 239 journals: 239 identical verdicts, 0 differences. No journal's last-modified time changed.

6. A bug found along the way — the ironic one

While building the size-trimming logic, the tool froze on one journal: over 100 seconds, no output, no error message.

The cause is a genuinely nasty quirk. The code repeatedly halves a range to find where to cut. In this scripting language, halving (1+2) and rounding gives 2, not 1 — it rounds to the nearest even number. That meant the “halfway point” could land on the end of the range, the range never got smaller, and the loop ran forever.

This mattered far more than a normal bug: a tool built to prevent runs from hanging, which itself hangs, is worse than doing nothing. It is fixed two ways — the arithmetic is now written explicitly, and both loops carry a hard limit so that even a future mistake stops safely instead of freezing the schedule.

7. How we know the safety checks actually work

A safety check that has quietly stopped doing anything still reports success. So the checks are themselves tested, by deliberately breaking the tool in six ways and confirming each break is caught:

Together with 15 checks on normal behaviour, that is 21 out of 21 passing. Two of these arms exist only because the first version of the test passed while proving nothing — the fake journal put its bulk in the one place the tool deliberately ignores, so the size limits were never actually exercised. That was found and fixed.

8. What this does not fix

The journals themselves are still growing, and there is still no policy for retiring old entries. That is a separate, known piece of work. What changed is the consequence: an oversized journal used to mean “tonight's run will burn most of its reading budget on this file”. Now it only means “this file has no cleanup policy yet”.

The size alarm was deliberately left switched on, so that if any journal grows more than 15% beyond where it is today, it still raises a flag.

9. How to undo it

Revert the one commit. Because the new tool only ever reads, removing it cannot leave any journal in a modified state — there is no change to roll back on your data. The only visible difference is that the assistant's instructions go back to saying “read the whole journal”.
