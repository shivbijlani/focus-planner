The settings file grew until the agent could no longer read it

What went wrong, why it stopped the automation from finishing, what was done about it tonight — and why that is a stopgap rather than the fix.

  • Issue 262
  • Pull request 287 merged
  • What shipped →
  • The approach →

One configuration file, user-settings.md, is read at the start of every Overnight Agent run — and it is also where the agent writes its own notes after every run. So it kept growing. It reached about 950,000 characters, which was roughly 97% of everything the model is allowed to read in one call. Runs stopped finishing. Eventually the agent's own file reader refused to open it at all.

The fix moves the accumulated notes into a second file beside it, leaves an index behind, and deletes nothing. Applied to the real file, it went from about 947,000 characters to about 75,000 — roughly 237,000 tokens down to about 19,000 — with all 41 settings rows intact.

The one-line version

The agent's notepad and the agent's config were the same file, and that file was on the read-every-single-time path. Tonight's change separates them — but that is containment. The durable fix is that the file was holding four different jobs at once, and each needs its own home. Section 7 is that argument.

1Why a big file stops the automation from finishingWhy “the file is big” turns into “the automation never finishes”.

The model can only look at a fixed amount of text per call. Think of it as a desk with a fixed surface area. Everything the agent needs — the instructions, the planner board, the task journal, the code it is reading, and its own work-in-progress — has to fit on that desk at the same time.

The instructions say: read user-settings.md first, every run. So the first thing that lands on the desk is the settings file. And because each step of a run re-sends the whole conversation so far, that file is not paid for once — it is paid for again on every single back-and-forth with the model.

When the settings file alone takes ~97% of the desk, three things happen at once:

  • Each step accomplishes almost nothing, because there is nearly no room left for actual work.
  • So the run needs far more steps — and every one of those steps re-reads the same giant file.
  • Every step is slow and expensive, because cost and latency scale with how much text goes in.

The result is not an error message. It is a run that grinds forever and never reaches the end. And because the schedule will not start a new run while the previous one is still marked running, one stuck run freezes the whole every-30-minutes cadence behind it.

One measured run made 49 round-trips to the model, averaging 239,624 input tokens each. The settings file by itself accounted for about 232,500 of those. It sat in running for roughly nine hours and never finished. (issue 262)

The file doubled roughly every week, because every run appended to it and nothing ever removed anything. These sizes are read off the timestamped backups sitting next to it:

Nothing was misbehaving. Writing down what you learned after a run is the correct instinct. The mistake was that the notepad and the config were the same file, and that file was on the read-it-every-time path.

2Then it crossed a second lineThe file got too large for the agent to read its own configuration.

Context pressure is a gradual problem — things get slower and worse. The second failure was abrupt. The agent's file-reading tool has its own size limit, and the file went past it:

File too large to read at once (946.0 KB)

Put plainly: the file that tells the agent how to behave became too large for the agent to read. On that run it could not load its own configuration, and had to reconstruct the settings table by searching the file for individual lines instead of reading it. That is not a degraded mode anyone designed; it is the automation improvising around its own config.

3What the shipped change doesSplit in two, verbatim, with an index left behind. Nothing deleted.

The change adds one script, split-user-settings.ps1, wired into the start of each run. It splits the file in place into two:

FileWhat's in itRead when?
user-settings.md The actual settings — paths, accounts, allow-lists, preferences, browser slots. Every run.
agent-lore.md Everything else — the dated run learnings, postmortems and hazard write-ups. Verbatim, in original order. Only when something specifically calls for it.

Concretely it does three things. It moves every ## section that is not on a keep-list into the lore file, character for character. It leaves behind a short index listing every heading it moved. And for the settings rows that stayed, if a single table cell has grown enormous, it keeps the operative part of the value in the cell and moves the trailing essay to the lore file behind a link.

The insight that makes this safe

In this particular file, the archived headings state their own rule — things like “STOP — RELIABILITY IS ALWAYS HIGH PRIORITY” and “STOP — Keep turns short”. So a list of the headings carries nearly all of the behavioural signal at roughly 1% of the characters. The agent still sees every rule's name on every run; it only pays for the full text when it goes looking. And nothing is deleted — the complete text is one search away.

Why the keep-list is written out by hand instead of worked out automatically

The list of sections that stay is short and literal: Settings, Telegram, Preferences, Browser slots, plus the file's opening paragraphs.

The tempting alternative is a rule like “keep any section that contains a settings table”. That rule is wrong here, because “has a table” and “the agent acts on this” are different questions. Both Preferences and Browser slots contain no table at all and are load-bearing; an inferred rule would have archived both.

A hand-written list also has a second property that matters more over time: it cannot quietly expand. An inferred rule keeps more and more as the file changes shape — which is precisely how the read-every-time path grew to a megabyte in the first place.

5The guards, and what each one is forSix refusals to proceed, each proven load-bearing by mutation testing.

The script rewrites a file that lives in your OneDrive and is the only copy of its own history, unattended, on a timer. So most of it is not the splitting logic — it is six refusals to proceed. Each one exists because of a specific way this could go wrong quietly.

The guardWhat happens without it
Put it back together first. Before writing anything, reassemble the original from the pieces and require an exact match. Any mismatch aborts with nothing written. A split that silently dropped a settings value would hand the agent a wrong path or a wrong allow-list — and look perfectly healthy doing it. That is worse than the bloat.
Back up before the first byte. The backup is written before any output is. A crash halfway through the write would leave you with a half-written file and no original.
Say the text encoding out loud, both directions. Windows PowerShell 5.1 assumes a legacy encoding for files like this one. Read it wrongly and write it back, and every accented character and emoji is permanently replaced with garbage — silently, reporting success. That exact failure destroyed 593 lines of a task journal a few days earlier.
Running it twice must change nothing. A second run writes literally zero bytes. This runs every 30 minutes against a cloud-synced file. A script that appends a little on each pass is a second growth problem wearing the fix's clothes — and every needless rewrite is another sync event and another backup file, forever.
Never break a table row. A shortened row must still have the same number of cells, and the cut may not land on an escaped pipe character. See the next section — this is the one that could corrupt your file through the web app.
Check the bytes on disk afterwards, and roll back. Re-read both output files and count the byte patterns that are the fingerprint of mangled text. If the output has more than the input did, restore the backup and fail. Corruption that every in-memory check passes can still reach disk. This is the standing proof that it didn't — and it caught a real instance (see the appendix).
These aren't decorative

A companion script, mutcheck-split-settings.ps1, deliberately breaks each guard one at a time and confirms the script then fails. Running it on this branch: 13 baseline checks pass, 6 sabotages introduced, all 6 caught. Every guard is doing work. A safety check that has quietly stopped mattering still reports success, which is the exact failure mode this catches.

6Why this is safe for the planner web appThe settings editor saves by byte offset, so a broken row would corrupt the file.

The planner's settings editor does not regenerate user-settings.md when you save. It finds the exact character positions of the one value you changed and splices the new text in, leaving every other byte untouched — see src/config/userSettingsForm.js.

That design is why it never mangles your file, and it is also why a malformed table row here would be more than cosmetic. A row the parser reads incorrectly wouldn't just look odd in the editor — it would mean the next time you save any setting, the splice lands in the wrong place and corrupts the file.

So the check (verify-settings-form.mjs) runs the before-and-after files through the web app's own shipped parser, not a reimplementation of it. Two things must hold: every settings row still parses, and reading the file and writing it straight back must return it completely unchanged. Both hold, on both sides:

7Why this is containment, not the cureFour different jobs were sharing one file. The same bug is in three places.

Everything above describes moving the notes out of the way. It works, and the numbers are real. But it treats the file as one thing that got too big, and that is not what happened.

Sorting the archived material by what kind of thing it is shows four different jobs that had been sharing one file:

What it actually isSectionsCharsShare
Dated run learnings — history103677,74475.6%
Operative rules — STOP notices the agent must obey23101,90311.4%

That last row is the diagnosis. One "setting" is an 8,479-character root-cause analysis of an unrelated startup failure, living in a table cell. It is not a setting. It is an incident report that was written where a value belongs.

Which means

The cell-trimming stage, the rule about keeping table rows intact, and the whole byte-offset-splicing verification exist only to make prose-in-a-value-cell survivable. If values were values, none of that machinery would need to exist — let alone be guarded.

The same bug is in at least three places

This is not one file that misbehaved. It is a pattern with no owner: nothing the agent writes to has a retention policy.

The journal figure is worth pausing on. When that issue was filed it measured 235 files and 2.26 MB. It is now 386 files and 4.89 MB — it more than doubled while the issue sat open, which is the same curve the settings file ran.

And the lessons issue is the sharpest evidence, because it predicted this file by name. It proposed distilling run retros into lessons.md, plus a consolidation pass to "compress the day's hard-won lessons." The append half shipped. The compaction half never did. What exists today is that proposal with its second half missing.

The settings file was not special because it grew. Journals grew too. It was special because the file that grew was also the file read on every single call. That is what turned untidy into fatal.

Why most of those 23 rules should be code, not prose

The STOP notices average 4,431 characters each — about 25,000 tokens if they were simply moved to another file that is also read every run. Relocating them would recreate this same problem more slowly.

A rule with a check does not need to be prose the model reads. It needs to be a check that fails. That moves the cost from context — paid on every call, forever — to execution, paid once per run. Prose is only load-bearing for judgement that cannot be mechanically tested.

One caveat, and it is a real one: an existing proposal to split these into partial files (#127) deliberately requires every guardrail to stay in a static file the model reads inline, never emitted as script output — on the grounds that a rule the model cannot see is a rule it cannot weigh. Both positions are defensible and they have not been reconciled.

9What is deliberately not donePreferences kept whole, and the decision the merge did not settle.

The Preferences section is kept whole. It is about 30,000 characters — roughly 40% of what remains — and unlike the archived material, it is prose the agent acts on directly rather than a list of named rules. Trimming it bullet by bullet would get the file meaningfully smaller (the pull request estimates under ~25 KB), but it trades away nuance in instructions you actually rely on. That is a judgement call about your own preferences, so it is left for you rather than assumed.

The change is now live. Pull request 287 was merged and the script is deployed, so the settings file is re-shrunk automatically on every run. That closes the bleeding — and it means the standing cost is now a script that rewrites a cloud-synced file on a timer, forever.

The decision the merge did not settle

Merging bought back the context window. It did not answer whether a rewriter was the right instrument. The issue's own second suggestion — "enforce a hard size cap on what's read at run start; fail loudly if exceeded" — was never built, and it is the cheaper, safer shape: a check that refuses to run cannot corrupt the file it is protecting. That is what shipped tonight alongside it.

The open decision

Merging that pull request buys back the context window and stops the bleeding, at the cost of a script that rewrites a cloud-synced file on a timer forever. Not merging it means hand-fixing the file periodically until the four homes above exist. The issue's own second suggestion — "enforce a hard size cap on what's read at run start; fail loudly if exceeded" — is a third option that was never built: keep the split as a one-time cleanup, and replace the every-run rewrite with a tripwire that refuses to run rather than quietly repairing.

10What shipped tonightA contract, a tripwire, and three issues. Read this first if you read nothing else.

Two things landed in the planner, and three issues were filed for what remains.

1. The file-layout contract, as data

read-path-manifest.json gives every file the agent touches one row stating four things: who owns it, who may write it, whether it is on the per-run read path, and what bounds its size. The rule it encodes is a single sentence:

No file may be both agent-appended and read on every run.

That combination is the bug, stated once instead of re-diagnosed per file. It caused this issue on the settings file and is causing it again on the journals. Declaring it as data means a third instance gets refused when it is written, not diagnosed after it breaks a night's work.

2. A tripwire that refuses, instead of a rewriter that repairs

read-path-budget-sweep.mjs runs with the existing nightly checks and fails loudly when anything on the read path exceeds its budget. It is the suggestion this issue made and nobody built.

The distinction that matters: it never writes. Most of the merged script's 492 lines are guards that exist because it writes — back up first, UTF-8 both directions, byte-exact reassembly, idempotency, preserve the row shape the settings editor splices by offset, roll back on mojibake. A read-only check needs none of them, and it cannot corrupt the file it is protecting or produce a cloud-sync event every thirty minutes.

Designed against a failure this repo already paid for

Seven journals are over budget today. Failing on all seven every night would make the check a permanently-red line — and a permanently-red line is one the next run learns to skim. That is not hypothetical here: a dead watchdog was flagged in 16 consecutive runs and nobody acted, for exactly that reason.

So known breaches are recorded in a baseline and reported as acknowledged. Growth past tolerance still fails — and growth is the real signal, because growth is the defect. Night one is green, with all seven visible.

Verification, using this repo's own convention: 19 assertions, 7 mutations, all killed. Each mutation re-opens one hole and must be caught by its own guard. One of them makes the sweep write a file, so the read-only property is tested rather than claimed.

What I did not do

I did not remove the merged rewriter. It works, it is deployed, and replacing a live fix at 3am on the strength of an argument is exactly the move that turns one problem into two. The tripwire runs alongside it and is the safer instrument; retiring the rewriter in favour of it is a decision worth making awake, and it is written down in #293.

Appendix — three real defects the guards caught while this was being built

History, not required reading. Included because each one is a bug class worth recognising again, and each is the reason a specific guard exists.

1. The script corrupted text it never touched

The first live-shaped run wrote 94 mangled character sequences to disk. The cause was not the data file — it was the script itself. Windows PowerShell 5.1 reads a script file with no byte-order mark using the legacy Windows codepage, so the few non-ASCII characters in the script's own source (an ellipsis, an arrow, an emoji) were already garbage the moment the script loaded, before they were ever written anywhere. Every in-memory check compared garbage to itself and passed.

This is the same encoding hazard the settings file itself documents, one layer up: not the data, the tool. The fix was to make everything the script emits plain ASCII, so the host's decoder cannot matter — and the byte-level check after writing is the standing proof that it stays that way.

2. A type annotation silently archived the file's own introduction

The function that decides whether a section stays declared its parameter as a string. PowerShell converts a missing value to an empty string when binding to a typed parameter, so the test for “this section has no heading” never fired. The only section without a heading is the file's opening paragraphs — the part that explains what the file is — and it got moved to the archive.

The alarming part: the split reported success and every guard passed. It only surfaced because the file came back starting abruptly at ## Settings. There is now an explicit check that whatever the source opened with still opens the result.

3. The shrinking tool was itself a growth engine

The index of archived headings that the script leaves behind is, structurally, just another ## section. So on the next run the script found it, decided it wasn't on the keep-list, archived it into the lore file, and appended a fresh one. Every 30 minutes, forever.

The tool built to stop a file growing without bound was quietly growing it without bound — the original bug wearing the fix's clothes. The script now strips the previous index before it starts parsing, which makes running it twice a genuine no-op.
